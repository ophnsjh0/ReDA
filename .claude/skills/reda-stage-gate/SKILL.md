# ReDA 단계 검증 (stage gate)

`기획안/검증기준.md`가 기준의 원본이다. 이 skill은 그 기준을 확인하는 순서만 정한다. 기준과 이 문서가 다르면 검증기준.md를 따른다.

## 0. 준비

1. 사용자가 어느 단계를 검증하려는지 확인한다. 말하지 않았으면 현재 브랜치 이름(`stage-<번호>-…`)이나 `기획안/구현계획.md`의 진행 기록에서 추정하고, 추정했다고 밝힌다.
2. `git branch --show-current`가 `main`이면 멈추고 알린다. `/security-review`와 `/code-review`는 브랜치의 아직 합치지 않은 변경을 검토하므로, `main`에서는 검토할 변경이 없다. `stage-<번호>-<이름>` 브랜치를 만들자고 제안한다.
3. `git diff main...HEAD --stat`으로 검토 범위를 확인해 둔다.

## 1. 자동 게이트

- **G1 테스트:** `uv run pytest -q`. 실패하면 출력 그대로 보고하고 원인을 찾는다. 새로 추가한 기능에 테스트가 없으면 실패로 본다.
- **G2 발송 차단:** `uv run pytest -q tests/test_no_send.py`.
- **G3 공개 저장소 위생:** 이 저장소는 공개다.
  - `기획안/운영메모.local.md`를 읽어 서버 주소, 계정 이름, uid, 호스트 이름, Tailscale 주소 같은 운영 값을 뽑는다. 이 값들을 이 skill 파일이나 커밋할 파일에 적지 않는다.
  - `git diff main...HEAD`와 `git ls-files`에서 그 값들, 그리고 비밀 형태(`BEGIN .*PRIVATE KEY`, `sk-[A-Za-z0-9]`, `refresh_token`, `client_secret`, 문서용 대역이 아닌 실제 IPv4)를 검색한다. 문서용 대역(192.0.2.x, 198.51.100.x, 203.0.113.x)과 `example.com`은 허용한다.
  - `.env`, `token.json`, `credentials.json`, `*.local.md`, `진행내역/`, `tests/private/`가 `git ls-files`에 없는지 확인한다.
  - 찾으면 값 자체를 출력하지 말고 "파일:줄에 운영 정보가 있음"으로만 보고한다.

## 2. 검토 skill

- **G4 보안 검토:** `security-review` skill을 실행한다. 높음 등급이 하나라도 있으면 게이트 실패다.
- **G5 코드 검토:** `code-review` skill을 `high` 수준으로 실행한다. `max`·`ultra`는 사용자가 직접 요청할 때만 쓴다.
- 두 검토의 지적 사항을 검증기준.md의 판정 등급(높음/보통/낮음)으로 다시 분류한다. 기획안 설계 제약을 어기는 지적은 원래 등급과 관계없이 높음으로 올린다.

## 3. 설계 제약과 단계별 기준

- **G6:** 검증기준.md의 "설계 제약 점검표" 중 이번 단계와 관련된 항목을 코드로 확인한다. 확인한 위치(파일:줄)나 테스트 이름을 근거로 적는다.
- 해당 단계의 "단계별 기준" 표를 한 줄씩 확인한다.
  - **자동 테스트 항목:** 그 기준을 검사하는 테스트 이름을 찾는다. 없으면 실패로 본다.
  - **수동 항목:** 직접 할 수 없는 것(실제 Gmail, VPS, 메신저)은 "수동 확인 필요"로 표시하고, 사용자가 실행할 명령을 적는다. VPS 확인은 읽기 전용 명령만 직접 실행할 수 있고, sudo가 필요한 것은 사용자에게 넘긴다.
  - **골든 세트 항목:** `tests/private/`가 없으면 "평가 세트 없음"으로 표시한다. 통과로 치지 않는다.

## 4. 보고

다음 형식의 표로 보고한다. 통과하지 못한 것을 숨기지 않는다.

| # | 항목 | 결과 | 근거 |
|---|---|---|---|
| G1 | 테스트 | ✅ 통과 / ❌ 실패 / ⏳ 수동 확인 필요 | 명령 출력 요약, 파일:줄, 테스트 이름 |

마지막에 한 줄로 판정한다: **합칠 수 있음** / **고친 뒤 다시 검증** / **수동 확인 후 판정**.

## 5. 기록

- `기획안/구현계획.md`의 해당 단계 "진행 기록"에 날짜, 판정, 실패·보류 항목을 적는다. 운영 정보는 적지 않는다.
- `진행내역/진행내역.md` 타임라인에 시각과 결과를 추가한다.

## 하지 않는 것

- 사용자의 확인 없이 `main`에 합치거나 push하지 않는다.
- 게이트를 통과시키려고 테스트를 지우거나 기준을 낮추지 않는다. 기준을 바꿔야 한다고 판단하면 이유와 함께 사용자에게 묻는다.
